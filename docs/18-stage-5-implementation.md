## 1. 当前结论

阶段 5 的功能主链路已经实现：Agent 不再只返回一段带来源列表的文字，而是先形成
任务内证据工作区，再生成原子 Claim—Evidence 图谱，由协议校验器检查引用完整性，
并在范围、时效、冲突或支持关系存在风险时调用独立语义 Verifier。回答、主张、引用
关系、核验摘要和性能轨迹均已进入正式数据模型。

阶段 5 已关闭。KISS 单查询 FTS 主链路、48 条检索回归和本地工程检查均已完成；
48/48 个用例的预期材料位于 Top 8，完整官方标题 Top 3 为 100%，63 次查询热态
P95 为 110.461ms。两道真实 Agent 合并黑盒回归已 2/2 通过。上述数字只是历史
实现记录，不再要求追加性能分桶或独立标注集。

## 2. 已实现内容

### 2.1 可信回答链路

- `EvidenceWorkspace` 为一次任务分配稳定证据 ID，同一官方页面的新观察不会破坏
  已建立的引用关系。
- Answer Composer 在一份结构化结果中完成证据充分性评价、事实/分析/建议区分和
  Claim—Evidence 映射。
- 中间调查轮若仍需补查，只返回缺口和最小补查步骤，不生成下一轮必然废弃的完整
  答案。
- `CitationVerifier` 只做协议确定性检查：证据 ID 是否属于本任务、校园事实是否有
  支持引用、回答 URL 是否属于本任务证据。它不使用正则或关键词判断语义真假。
- 独立语义 Verifier 检查蕴含关系、年份、适用对象、政策范围、历史规律和当前安排；
  通过时复用候选答案，修订时只输出结构化差异补丁（见 2.5）。
- 最终仍不通过引用协议时，协调器降级为不包含无证据校园事实的透明说明。

### 2.2 数据与 API

数据库迁移 `0006_stage5_grounding_performance` 新增：

- `answer_grounding`
- `answer_claims`
- `claim_evidence`
- `task_performance`

回答 API 新增 `claims`、`grounding` 和 `performance`。性能对象包含模型/工具 span，
可以直接定位首字等待、生成、浏览器查询和本地处理耗时。前端在校园事实引用覆盖
完整时显示“主张已映射”状态。

### 2.3 性能计量与基准工具

每个模型调用记录请求开始、首个文本/拒绝增量和完成时间。阶段 5 可控延迟从任务
墙钟时间中扣除所有“模型请求开始到首个输出增量”区间的并集；无法测得首输出的
样本在历史报告中单独标记。

`apps/api/scripts/report_stage5_metrics.py` 可从 SQLite 或 PostgreSQL 汇总：

- 四类场景的 P50/P95/P99 可控延迟；
- 模型往返次数 P95；
- 首个进度事件 P95；
- 引用覆盖与完整支持标记；
- 不可测首字样本和结构化核验错误。

脚本曾支持按场景汇总样本，并把没有人工标签的引用统计明确标为
`requires_labeled_evaluation`。该能力保留用于按需诊断，不要求建立标注项目。

### 2.4 实时查询关键路径

- aTrust 登录会话继续复用，不为每条工具调用重复登录。
- 侧车按软相关顺序读取候选，取得调用方请求数量的可读页面即停；未读页面仍可在
  语义补查中继续访问，不会被宣布为无关或不存在。
- 单轮详情读取预算由原来的 `limit × 4` 降为 `limit + 4`，且实际拿满结果即可提前
  结束。
- 来源可见性不再获得无条件排序加分，避免“已登录来源”压过与问题真正相关的公开
  学院或教务来源。
- 只有图片标题与查询有关，或正文提取不足 160 字时才调用图片模型。页面标题作为
  无 `alt/title` 图片的回退标题，因此校历等正文图片仍能被识别。
- aTrust 回落门户只重试一次，避免已失效站点在每个候选页上重复长等待。

### 2.5 租约批处理与差异修订（2026-07-26 实现）

按 5.1—5.3 的设计完成工程实现，CI 门槛（ruff、迁移、后端 45 项测试、前端
typecheck 与 build）全部通过：

- `search_campus_notices_live` 支持 `queries`（最多 4 条），协调器把同一并行
  批次中的多个校园通知步骤合并为一次批查询；合并步骤代表全部原始步骤 ID，
  `depends_on` 解析不受影响。中心 API 请求同时携带 `query` 与 `queries`，
  旧版 sidecar 自动降级为服务首条查询。
- sidecar 在一次租约锁内完成整批：来源排序取各查询最大分，每轮只做一次页面
  发现，候选按“每查询独立排序 + 轮转”读取，同一 URL 全局只读一次；调度逻辑
  为纯函数并有独立策略测试。`search_trace.per_query_result_counts` 区分单查询
  零命中与整批未查完。
- `ClaimCitation.supporting_excerpt`/`rationale` 增加 schema 长度上限，Composer
  提示要求最短定位片段、完整支持不写理由、analysis/advice 段落级合并。
- `AnswerVerification` 改为 `revision` 差异协议：`ClaimPatch`（remove/replace/
  add）加实际变更字段；`apply_answer_revision` 确定性应用补丁，补丁改动主张但
  未提供修订正文视为协议违规并降级。应用后仍重跑 `CitationVerifier`。

以上属于关键路径工程优化，实际可控延迟收益需按 5.5 用真实登录态样本验收。

### 2.6 SQLite FTS5 单查询主检索（2026-07-27 实现）

旧的多查询累计/取最大值打分、公平轮转、共享候选池、chunk 向量扫描和
Coordinator 正则重排已从正常回答链路删除。当前主检索保持一个可解释边界：

- 启动时幂等创建 `campus_search_fts_v1`，使用 FTS5 `trigram` tokenizer，索引全部
  `DocumentVersion` 的标题和正文；首次部署自动回填，文档版本增删改由 SQLite
  trigger 同步。该表是可丢弃派生数据，`reindex-memory` 可完整重建。
- 每次 `search_campus_memory` 只接受标量 `query` 和 `top_k`（默认 8，范围
  1—12）。查询只做 NFKC、空白、引号和连接号语法归一化，然后独立执行 BM25；
  标题权重 5、正文权重 1。
- 查询先以短语 AND 和既有两字短语精确条件执行；只有严格候选为 0 时，才执行
  一次短语 OR 并移除两字短语条件。返回第一个非空结果集，不跨查询累计分数，
  不做 trigram OR、词表扩展或 Coordinator 重排。
- FTS 命中后通过关系表限定当前版本、启用来源、服务端身份可见范围、允许质量
  状态和 2023-01-01 时间边界。相同 URL 去重并保留搜索引擎顺序。
- 返回 FTS 命中片段；镜像证据 `fresh_until=null`，不再生成逐文档 TTL 警告。
- 既有 chunks、embedding 与 entities 继续服务采集、管理和历史审计，但不参与
  主检索。本阶段不建设 ANN 或 PostgreSQL 搜索兼容层。

### 2.7 Agent 调查与核验简化（2026-07-27 实现）

- `Prepare` 正常首轮最多生成 3 个本地步骤，每个步骤对应一个独立信息点和一个
  简短官方表述；独立本地步骤由 Coordinator 并行执行。查询最多保留两个空格
  分组，模型需优先生成“核心事项 + 所求事实”的完整名词短语；同一信息点不安排
  多个近义查询。缺失 query 的无效模型步骤在执行前丢弃。
- 证据按规划步骤和各 FTS 结果内部顺序进入工作区，最多 24 条。Coordinator 不再
  使用停用词表、n-gram 或 `_rank_evidence` 二次排序。
- Composer 仅在某个子问题缺关键证据时追加一轮；必须先用更短或更正式的表述
  重试一次本地检索，之后才可请求工具目录中实际可用的校园或公开实时工具。
- 校园实时路由关闭时，工具完全不进入模型目录；`Campus` 身份本身不会使一个
  不可用路由看起来可用。本地证据充分时不得调用公开实时搜索。
- 普通回答只运行结构化引用校验。独立 Verifier 仅由学业高风险/敏感问题、官方
  材料冲突或引用结构失败触发；历史材料用于概括规律本身不触发 Verifier。

### 2.8 通用采集质量与模型流兼容（2026-07-27 实现）

- HTML 标题抽取在站点 `<title>` 之前检查 `.news_detail h2`、`.contenter h2`、
  `article h2` 和通用 24px 加粗文章标题；HTML parser 版本升级到 v6。现有资源
  在正常同步时自动重解析，不为 6926 或固定验收题增加特例。创新训练来源普通
  增量同步已重解析 22/23 个页面，剩余 1 页为源站 HTTP 500。
- Windows OCR v2 保留词坐标并按视觉行重组，日期/事项或字段/值不再被拆成两个
  无对应关系的列；旧 OCR 版本可通过可恢复的重处理参数升级，无需重新抓取原图。
- 部分 Relay 会在 `response.created` 前发送 `codex.*` 厂商事件。首次发生
  输出前流协议失败时，Model Gateway 回退 `responses.parse` 并在当前进程记住
  非流式模式；后续调用不再重复一次必败的流请求。该次 TTFT 仍标记为不可测。

### 3.2 批处理与差异修订历史复测（2026-07-26）

第二问相比上一版：可控耗时 198.5s → 136.2s（约 -31%），VPN 批量检索

该次第二问的功能失败已由最终引用协议两级修复和 2.6 的广召回改动修复；表中
136.2 秒仍是当前最后一个可比较的多来源可控延迟样本，不代表最新功能结论。

## 5. 阶段 5 已完成的收尾实现

### 5.1 租约感知的校园查询批处理

`search_campus_notices_live` 接受最多 4 条短查询，一次调用在同一浏览器租约内
完成整批：

- 来源排序按各查询取最大分，避免某条长查询把真正相关的来源压到后面。
- 每轮扩搜只做一次页面发现；候选读取顺序由“每查询独立排序 + 轮转”决定，
  同一 URL 全局只读取一次，其结果可同时服务多条查询。
- 单轮读取预算随查询条数线性扩展，停止条件是每条查询各有至少一条可读证据或
  预算耗尽。
- `limit` 语义是每条查询的证据上限，整批合计不超过 16 条。
- `search_trace` 增加 `per_query_result_counts`，让 Agent 区分“该查询零命中”与
  “整批尚未查完”。

调度逻辑抽为纯函数，可在无浏览器环境下做策略测试。协调器在同一并行批次内合并
多个校园通知步骤，属于执行层调度，不改变规划语义，也不把多个主题压成一个长
查询。浏览器网络策略、能力校验与只读边界不变。

### 5.2 Claim 输出纪律

`supporting_excerpt` 只保留能定位原文的最短片段并受长度上限约束；完整支持且
关系为 supports 的引用不再重复写 rationale；analysis 与 advice 按段落粒度合并，
campus_fact 仍逐条原子化。目的是压缩最终 Composer 的生成时间，不降低引用覆盖或
支持判定的粒度。

### 5.3 Verifier 结构化补丁协议

Verifier 通过时不再回传候选答案。需要修订时只输出实际变更的回答字段，以及按
主张 ID 表达的 remove/replace/add 补丁；未修改主张一律不重复生成。补丁涉及主张
增删替换时必须同时给出修订后的正文，否则按协议违规降级。补丁由确定性纯函数应用，
应用后重跑引用协议校验作为安全网。

### 5.4 最终引用协议失败时的两级修复

3.2 复测证明“修订失败即整份降级”会丢弃已被证据确认的事实。最终引用协议校验
失败时，协调器按顺序执行：

1. **确定性修剪**：删除指向本任务证据工作区之外的 evidence_id 引用；把正文中
   指向工作区外 URL 的链接剥离为纯文本；仍有有效支持的主张全部保留。修剪后
   重跑引用协议，通过即输出。
2. **轻量引用修复调用**：一次 utility 模型调用，输入只含失败 findings、候选
   回答与证据工作区的 evidence_id/标题/摘录列表。只允许重新绑定到真实存在的
   evidence_id、调整支持状态、或删除无法支持的主张并同步修订正文；禁止引入新
   校园事实。输出复用 AnswerRevision 差异协议，应用后重跑引用协议，通过即输出。
3. 两级修复后仍不通过才降级为不包含无证据校园事实的透明说明。

修复调用只在失败路径触发，不增加正常任务的模型往返。
